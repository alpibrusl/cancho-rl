# cancho-rl

Reinforcement learning on [cancho-gpu](https://github.com/alpibrusl/cancho-gpu), for language models first and small control policies for cancho-robot second: rollouts, rewards, advantage estimators, the policy-gradient step and the experiments that measure them. The kernels, sessions and runners stay in cancho-gpu; the environments stay in `cancho-code` and `cancho-robot`.

**Status: R0 to R3 are done, R4 has run twice, and the whole iteration and the loop are driven from cancho.** Everything below is measured and written up in [`docs/design.md`](docs/design.md) (sections 27 to 48), with the logs in `docs/r1/` and `docs/r4/`. Read the design first: what is in cancho-gpu, the milestones and their exit criteria, and the limits of each number.

- **A grader** (`rl grade`): the compiler builds the candidate, runs it against a hidden oracle under a wall deadline, and returns one JSON line. 104 small tasks (`branch` and `loop` kinds, a train/held-out split that is a function of the task's name), a gate that checks every reference and every hacking probe, and an independent Python port of the oracles for the first 34 tasks.
- **A reference run (R1)**, torch and peft on MPS: held-out solve rate 10.7% and 7.1% at step 0, 38.4% and 48.2% at step 40 (two seeds). Section 45 later found that its sampler kept the model's repetition penalty of 1.1 that the loss does not know about, so R1's curve is of that mismatched procedure and its baseline is not the model's.
- **The weighted policy-gradient step on the device (R2):** the gradient of a real batch agrees with torch's (cosine 0.99995 over 392 adapter matrices), with the advantage and the batch packed in cancho and AdamW over the 18.5 M LoRA values on the host.
- **Batched sampling on the device (R3):** a decode step for a batch of sequences (f16 weights, attention for a batch, the sampler, the loop that stays on the device), prefill with the caches saved eight times a prompt, and LoRA inside the decode step, each held to transformers or to a float64 reference.
- **R4, the loop:** 40 iterations of 4 tasks x 8 samples with held-out evaluations. Held-out rate **0.254, 0.402, 0.446, 0.469, 0.464** at steps 0, 10, 20, 30, 40 for seed 1, and 0.254, 0.478, 0.527, 0.513, 0.487 for seed 2, in about 92 minutes of one M4 Max. The run is reproducible bit for bit. One iteration takes about 63 to 82 s, 3.3 to 3.8 times R1's torch loop (a timing comparison, not a learning one). The floor is explained in section 45: with the penalty at 1.0 torch's step-0 rate is 0.268 and ours 0.254.
- **In cancho, not in a script:** `rl iterate` (one iteration, 95 data files byte-identical to the shell driver) and `rl loop` (the loop and the held-out evaluation; step-0 rate 0.254464, same as the shell loop, and the first iteration's parameters and moments byte-identical). The command line is `rl grade | split | prompt | chat | report | tasks | pack | adamw | rollin | complete | extract | samples | iterate | loop | ask`. Every refusal has a rule tag: `rl.usage`, `rl.task`, `rl.input`, `rl.ask.session`.

**Not done:** more than two seeds; a 40-iteration run through `rl loop` itself (one iteration is checked, the run takes about an hour); R1's loop rerun with the penalty at 1.0; the cancho initialiser of the starting adapters (Python's `qwen_ref.init_lora` makes them); the control track (a design, waiting on a simulator). The held-out tasks are 28 hand-written integer functions of the same family as the training tasks: the rise says the reward trains a model on this family, not that it got better at cancho in general.
