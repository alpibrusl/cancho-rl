## 1. What this is, and what it is not

`cancho-rl` is where reinforcement-learning *algorithms* live, for **any policy that can give the log-probability of its actions and take a weighted gradient step**: a language model (the first track, sections 2 to 7) and a small control network for a robot (the second track, section 4b): the rollout loop, rewards, advantage estimators, the policy-gradient loss and the experiments that measure them. It runs on top of [`cancho-gpu`](https://github.com/alpibrusl/cancho-gpu), which owns the kernels, the training sessions and the runners.

The split, and why:

* **cancho-gpu keeps the primitives.** A kernel, a session directive, a faster decoder, a numerically checked loss gradient. Its gate holds numerics to 1e-4 against torch and its documents are about the training stack; algorithms that change every week do not belong in it.
* **cancho-rl keeps the algorithms and the experiments.** GRPO, REINFORCE with a leave-one-out baseline, PPO if ever; reward functions; the evaluation protocol.
* **The environments stay where they live.** Tasks with a checkable reward for a coding model come from `cancho-code` (its eval harness and journals); a robot policy would come from `cancho-robot`'s simulator. `cancho-rl` calls them; they do not depend on it.

Not goals: a gym replacement or a catalogue of every algorithm (an algorithm is added when a track needs it and has a measured baseline), multi-GPU or NVIDIA training (cancho-gpu's CUDA path has run only kernels so far, not a training session), RLHF with a learned reward model.

**A framework with one instance built first.** The LLM instance (GRPO, language-model policies) is built first because its reward is checkable and its baseline is measured (section 2); the control instance (section 4b) is the second, and the seams between what is shared and what is not are in section 4c. The shared layer is not written ahead of the second instance: with one instance every guess about the seams is a guess, so the first instance is written with the seams named and kept clean, and the extraction happens when the second one shows which guesses were wrong. The control instance shares the parts that do not depend on the policy: the advantage estimators, the loss as a weighted log-probability objective, the evaluation protocol with seeds and bootstrap intervals, and the rule that a reference implementation in torch comes first. What differs is the regime: a language-model iteration is dominated by generating completions, a control-policy iteration by simulator steps and by many small gradient steps. Nothing in the algorithm layer may assume tokens, a vocabulary or a prompt.

## 2. The first target, and why this one

**GRPO** (group-relative policy optimisation: sample a group of completions per prompt, score each with a reward, use the reward minus the group mean as the advantage, no value network) with **LoRA** on a small Qwen (Qwen2.5-0.5B and 1.5B are the sizes cancho-gpu trains today), on **tasks with a verifiable reward from cancho-code**: write or repair a cancho program, reward from the compiler's check and the task's tests.

Why this combination:

1. No critic network: memory is the policy plus its adapters. cancho-gpu's 1.5B LoRA step is 19.4 GB at 4 x 512 tokens **[read: cancho-gpu `docs/resident.md` section 23]**; a second model would not fit comfortably next to rollouts on 64 GB.
2. **The reference policy is free with LoRA**: the same base with the adapter switched off gives the KL term's reference log-probabilities **[unknown: whether a session can run one forward with the adapters off; to be read in `examples/qwen/qwen_session.py` before R2]**.
3. The reward is checkable without a learned model, which keeps the experiment honest and cheap. It is also the place where the experiment can fool itself (section 7).
4. cancho-code's M8 experiment already asks "does tuning on cancho help the coding agent?" (cancho-gpu `docs/roadmap-models.md` section 7). RL on the same tasks is its natural next question, with a measured baseline from M8's arms.

**The decisive gap is rollouts.** A group of 8 completions of 512 tokens on the 0.5B is 512 decode steps of a batch of 8; at the measured 0.9 s a token that is about 460 s for one group **[derived]**, against a gradient step of about 0.9 s for 4,096 tokens **[read]**. An RL loop whose rollouts cost 500 times its learning step cannot be measured, let alone be fast. So **the order of the milestones is rollouts first** (R3 before R4), and the first working loop (R1) uses a different generator.

## 4. Milestones, each ending at a number

Exit criteria are fixed here, before building. Each milestone is a separate change with a gate that can fail.

**R0. A task set and a reward that can be trusted.** From cancho-code's tasks, a set where the untuned model sometimes succeeds and sometimes fails, so that there is a signal to learn from. Exit: (a) the reward is deterministic (the same program gives the same reward in 20 repeated runs, 0 disagreements); (b) on at least 200 tasks, split into train and held-out with the held-out tests never shown to any policy, the base model's pass rate with 8 samples per task is between 10% and 70% (outside that range there is nothing to learn from or nothing to measure); (c) a list of reward-hacking probes (an empty program, a program that prints the expected output, a program that exits 0 early) each scoring zero. Baselines recorded: the base model and, if M8 has finished, the M8 arms.

**R1. A reference loop in torch/peft on MPS (the oracle).** The same discipline as cancho-gpu's M7: first the established library, so that every later number has something to equal. GRPO with peft LoRA, torch on MPS, generation by the model's own `generate` or by MLX, rewards from R0. Exit: the held-out pass rate after N iterations is above the base model's by more than the spread of two seeds, with the seeds, the iteration count and the wall time recorded. If it does not rise, that is the result, and the milestones after it are not built on hope.

**R2. The policy-gradient step in a cancho-gpu session equals torch's.** One fixed batch of groups: the advantage-weighted loss and the gradient of every adapter against R1's, as cancho-gpu's M7.2 did. Exit: the loss within 1e-3 relative, every adapter gradient at cosine >= 0.995, a 40-step run whose training loss differs from torch's by under 1e-3 (the M7.3 pattern). Needs: the weighted loss kernel contract read (section 3), the reference forward with adapters off.

**R3. Rollouts at a usable speed.** A cached batched decoder for the Qwen2.5 sessions (or the existing runner extended), able to take freshly updated adapters. Exit: greedy tokens equal the R1 generator's on a fixed set of 8 prompts for 128 tokens (the M2 and M7.3 standard), and tokens a second for a batch of 8 completions reported against MLX and llama.cpp on the same model. **No target speed is set here**: the number is measured first, then the claim is made, because the competitors on this machine are fast and the honest question is whether cancho-gpu is within reach, not whether it wins.

**R4. The loop end to end on cancho-gpu.** R1's experiment with R2's step and R3's rollouts. Exit: the held-out pass-rate curve within the spread of two R1 seeds at every checkpoint, and seconds per iteration and peak memory reported against R1's. If the rollouts are still the cost (they will be, section 6), the report says what fraction of an iteration they take.

## 4b. The second track: small control policies (an outline; milestones are fixed when the environment has been read)

> **Corrected 2026-11-05, after reading `cancho-robot` and `cancho-afm` (this section was written naming only cancho-robot, and cancho-afm had not been considered).** What was read, and what it changes:
>
> * **cancho-robot has no simulator [read: `src/` is `feetech`, `serial`, `kinematics`, `ik`, `safety`, `rules`, `calibration`, `gate`, `check`, `so101`; no dynamics; no `simulat` in its README or design].** It has forward kinematics (`kinematics.forward`), a damped-least-squares IK (`ik.solve`, with status codes) and a safety core with rule tags (`rule_joint`, `rule_workspace`, `rule_ik_jump`, the collision rules, `rule_deadman`). Its decision "Training and policy inference are not in v1" and its rule *what learns cannot change the bounds* [read: `docs/decisions.md`, `docs/design.md` section 6] say how a policy attaches: **as a client that requests motion and reads refusals, never inside the controller.** So a robot instance of cancho-rl is a policy outside the controller whose every action goes through `safety`, and a refusal (with its rule tag) is part of the observation and the reward. The only environment that exists today is kinematic (reach a pose), where IK is an analytic baseline a learned policy has no reason to beat; so robot is **not** the first control instance. It is worth having later for one reason, the refusal-as-feedback loop, and it needs a simulator written first.
> * **cancho-afm has a software twin in cancho and a hand-written baseline [read: `docs/simulator.md`, `docs/tune-approach.md`].** `sim/board.cho` (the register interface of the board) with `sim/plant.cho` (a fork, a tip and a surface), `sim/pid.cho`, `sim/raster.cho`; a whole automatic run (several hundred thousand simulated conversions) takes about a second on the debug compiler; `sim/tune.cho` `choose` picks the drive frequency, setpoint and gains by a rule, and `host/metrics.cho` (`grating_fit`, `step_fit`) scores an image. The recorded baseline: the loop's image recovers about 89 pm of a 100 pm grating at 60 loop steps per pixel and about 108 pm at 120, the period at 5.9 to 6.0 pixels, and the approach never touches. Everything is in cancho, so a rollout needs no process boundary. **This is the first control instance**: reset with a seed (plant parameters, grating), act (choose the tune and scan parameters: gains, setpoint, steps per pixel, approach step and dwell), reward (image fidelity from `grating_fit` against the known truth, minus a large penalty for touching, per unit time since a high-speed instrument is the repository's second goal [read: its description]), baseline `tune.choose`. It is a few-step or one-step environment, not a long-horizon one.
> * **What the AFM instance does not claim:** the twin is the simplest model with the right shape and no measurement in it [read: `simulator.md`, "How far to trust it"]; a policy that wins on the twin has learned the twin. Nothing from it says anything about a real instrument, and the exit criteria must say so.
> * **Two honest checks the AFM instance must pass before RL is called useful:** (1) with an action of five or six numbers, a neural-network policy and PPO are a heavy tool; a seeded random search and an evolution strategy are the baselines to beat, and if they match PPO the result is "use them", recorded as the result (the same stance as section 4, R1); (2) the first test of the environment is whether `tune.choose` is beaten at all by *any* method, because if the hand rule is near the optimum on the twin there is nothing to learn. cancho-gpu's small-network advantage (above) is therefore **not** expected to matter here: a policy of a few hundred parameters is not the regime where launch overhead dominates, and the first AFM experiments need no GPU.
> * Relation to `cancho-ml` issue 59 (logged bandit feedback, off-policy evaluation, policy learning by reduction): the one-step form of the AFM instance is a contextual bandit, so `ml ope` could judge a learned policy from a log without rerunning the twin. It is a possible cross-check and not a dependency; nothing here waits for it.
>
> The paragraphs below were written before this reading; where they say cancho-robot's simulator, read the AFM twin first and cancho-robot second.

**Why it is worth having.** The measured wins of cancho-gpu over torch on MPS are on small networks, where launch overhead and fusion decide: the 60 M-parameter GPT step 15% faster, the MLP and CNN steps within a few percent either way, a CNN 1.6 times slower **[read: cancho-gpu `docs/resident.md` sections 13 to 19]**. A control policy is a small network (an MLP, or a small CNN on camera frames) updated many times, so the regime is the one where cancho-gpu has something to show; whether it shows it for RL is not known.

**First algorithm: PPO** (clipped surrogate, generalised advantage estimation, a value head sharing the trunk or a separate small network). It is the default baseline for continuous control; SAC or others are added only if PPO plus the task leaves a question they answer. **[open]**

**The environment.** cancho-robot's simulator, which owns the dynamics and the reward. What `cancho-rl` needs from it is an interface of a few calls (reset with a seed, step with an action, observation and reward, a done flag, a way to run many environments in a batch). Whether `cancho-robot` offers that, in a form callable from a session driver at the speed an RL loop needs, is **[unknown]** and is the first thing to read for this track. If the simulator is slow, the milestones below measure that before they measure anything about learning.

**Milestones (outline, exit criteria to be fixed before building each):**

* **C0. The environment and its baseline.** A task in cancho-robot with a reward and a way to run it in batches; a random policy and a scripted policy scored. Exit: environment steps a second, the reward of both baselines with seeds, and a check that the reward cannot be earned by a degenerate behaviour (the control analogue of R0(c)).
* **C1. A torch PPO reference.** Torch on MPS (or CPU, whichever is faster for these sizes), the same environment. Exit: the return after N environment steps above the scripted baseline's, with two seeds at least, or the negative result recorded.
* **C2. The PPO update in a cancho-gpu session equals torch's.** One fixed batch of trajectories: the loss and every parameter gradient against C1's, then a short run whose return curve is within the spread of two torch seeds. This is the point where the small-network advantage, if any, is measured: seconds per update against torch's.
* **C3. The loop end to end, with the simulator in the picture.** Report the fraction of wall time spent in the simulator, the policy forward, and the update. If the simulator dominates, the honest conclusion is that the update's speed does not matter for this task, and that is the result.

The risks of section 7 apply with the changes the regime brings: reward hacking appears as the policy exploiting simulator quirks (sim-to-real caveats stay in cancho-robot's documents; no number from simulation here says anything about the real arm), and RL on small networks is noisy enough that fewer than two seeds is not an experiment.

## 4c. The framework: six seams, and what is generic today (2026-11-05)

An RL run is the same loop whatever the policy is: *sample actions from the policy in an environment, turn rewards into advantages, take a weighted gradient step, measure on held-out instances*. The framework is the loop plus six interfaces; an instance (LLM, control) supplies the first two and shares the rest.

| Seam | What it is | LLM instance (first) | Control instance (second, outline) |
|---|---|---|---|
| **Policy** | `act(observation, seed) -> action, logprob`; `logprob(observation, action)`; `step(weights)`; adapter or parameter state to save and restore | Qwen with LoRA on cancho-gpu; an action is a completion (tokens) | an MLP or small CNN; an action is a vector |
| **Environment** | a named, seeded instance: `reset(seed) -> observation`, `step(action) -> observation, reward, done`; a one-shot environment is the special case of one step | a task from `tasks/<id>`; one step, the completion is the program; the reward is the grader's | a cancho-robot scene, many steps |
| **Rollout** | runs a batch of policy-environment episodes, records `(observation, action, logprob, reward, done)` | a sampling script (`scripts/sample.sh`, run in section 17) | simulator batch |
| **Estimator** | rewards of a group or trajectory to advantages: leave-one-out group baseline (GRPO), GAE (PPO) | group-relative, per task | GAE with a value head |
| **Objective** | advantages and logprobs to a weighted log-probability loss, with clipping and the KL term | token-level, masked to the completion | per-step |
| **Evaluator** | held-out instances, seeds, interval | pass rate at k samples, bootstrap interval | return over seeds, bootstrap interval |

Nothing above the line between Policy/Environment and the rest may assume tokens, a vocabulary, a prompt, a sandbox, or that a reward lies in [0, 1].

**What the code written so far is, said plainly [read from this repository: PR #2 and PR #3, both merged, the second holding `rl split`, `rl prompt`, `prompts/primer.md`, `scripts/sample.sh` and design section 16]:**

* **Generic already, and worth extracting later:** the held-out split rule (FNV-1a over an instance name, `tools/rl/main.cho`: `fnv`, `is_heldout`; it needs only a name); the reward record's shape `{id, reward, solved, status}`; the rule that a failure of the thing under test is a reward and never a failure of the trainer; the rule that a gate probe (an input that must score a known value) exists for every reward.
* **LLM-only, and staying in the LLM instance:** `lib/rl/grade.cho` (composes a test module from a candidate *program* and an oracle, runs `cancho test` under a deadline: the sandbox exists because the policy's output is untrusted code, which a control policy's is not), `rl prompt`, `prompts/primer.md`, `tasks/`, `scripts/sample.sh`.
* **Shared helpers, not a design question:** `lib/rl/text.cho`.
* The reward in the LLM instance is `passed/of` in [0, 1] plus `solved`; a control instance's reward is an unbounded return, so the record's `reward` is a float with no range promised and `solved` is optional. This is the first guess that would have been wrong if the framework had been written from the LLM case alone.

**Layout, and when it changes.** Today (2026-11-05): `lib/rl/{text,side,grade,report}.cho` and `tools/rl/main.cho` (`side` is the split rule, generic; `report` reads results files and is generic apart from the kind field; `grade` is LLM-only). The shared layer moves to `lib/rl/core/` and the LLM code to `lib/rl/llm/` **when the first control milestone (C0) starts**, as one change that moves files and nothing else, so the history shows what the second instance forced. Until then no file is renamed and no interface is declared in code that nothing calls. This answers open question 6 (section 9): one repository, one directory per instance, the shared layer extracted at the second instance.

**What would make this framework the wrong shape, stated now.** (a) If the policy interface needs the whole sampling loop inside cancho-gpu (as decoding on a fused kernel may require, section 6), `act` is a batch call into the session, not a per-observation call, and the Rollout seam is the session's. (b) If control rollouts need the simulator and the policy in one process to be fast enough, the Environment seam is a batch API (`step` over N environments), which the one-shot LLM environment satisfies trivially with N = the group size. (c) If the objective for the two instances differs in more than masking and the estimator, the Objective seam is two functions behind one name, and that is a finding, not a failure.

**Python and torch** stay what section 14 made them: in the control instance, C1's torch PPO reference is a comparison helper under `scripts/`, never a dependency of the package.

## 5. The experiment, stated before it is run

* **Model:** Qwen2.5-1.5B-Instruct is the first choice (the size M8 tuned and cancho-gpu trains in 19.4 GB); the 0.5B for fast iteration of the code. **[open]** the maintainer's call.
* **Algorithm:** GRPO with the advantage `A_i = (r_i - mean(r)) / (std(r) + eps)` over a group of 8, a KL penalty to the reference with a small coefficient, one gradient step per batch of groups (no PPO clipping at first: it matters only with several steps on the same samples). Learning rate, group size and KL coefficient are chosen on the *train* tasks and fixed before the held-out tasks are touched.
* **Seeds:** two at least for R1; fewer is not an experiment.
* **Success rule for "RL helps":** the held-out pass rate at the end is above the starting rate by more than the interval of the starting rate itself (a bootstrap over tasks, 10,000 resamples, a seed recorded), in both seeds. "Helps more than M8's supervised tuning" is a second, separate claim that needs the M8 result and the same held-out tasks.
* **What is reported whether or not it works:** the reward curve on train tasks, the pass rate on held-out tasks, the length of the completions over time (length collapse and loops are the usual failure; cancho-gpu's W0 repeat detector `examples/qwen/m8_loops.py` is a ready check for loops **[read]**), and the fraction of groups with zero reward variance (those give zero gradient and measure how hard the task set is).

## 6. Cost and where the time goes

* **Rollouts dominate** every RL loop of this kind; here more than usual, because the cached decoder for the training model does not exist yet (section 3). Until R3, an iteration is rollout-bound by orders of magnitude **[derived]**.
* **Memory:** policy weights (f16, 3 GB at 1.5B), adapters and Adam (small), activations for the gradient step (the 19.4 GB figure includes them), plus the generator's KV cache. Rollouts and the gradient step do not run at the same time in the first design, so the peaks do not add **[estimate]**; one GPU job at a time on this machine is a standing rule of the workspace.
* **R1 on torch/MPS** is the cheapest way to learn whether the *task set* gives a signal. It should be run before any cancho-gpu work, because it can end the project early at no kernel cost.

## 7. Risks, said now

1. **Reward hacking.** A checker that accepts "compiles" rewards trivial programs; a test the policy can see is a test it can memorise. R0(c) and the never-shown held-out tests are the defence, not a guarantee.
2. **No signal.** If the base pass rate is near 0 or near 1 on the task set, GRPO has nothing to learn from. R0(b) exists to find that out first.
3. **Small-model RL is noisy.** Two seeds can disagree. The success rule requires both; if they disagree the result is "not shown".
4. **Rollout speed decides feasibility, not the algorithm.** If R3 lands far from the alternatives on this machine, the right move may be to use MLX or llama.cpp for rollouts and keep cancho-gpu for the gradient step (R2 with R1's generator). That is a legitimate end state and is recorded as one.
5. **The M8 training this builds on was torch/MPS, not cancho-gpu** (its memory growth swapped the machine before it was fixed). Comparisons of tuned-model baselines must say which stack trained them.
6. **Everything measured so far is one Apple M4 Max.** No NVIDIA training run exists; nothing here claims one.

## 8. Working rules for this repository

Inherited from cancho-gpu and cancho, because they work:

* **Design before code**, in `docs/`, with claims marked as in this document. A claim that turns out false is corrected in place, in the document that made it.
* **The gate:** whatever the repository's gate script runs must pass before anything is called done; a test that cannot fail is not a test (each check is watched failing once).
* **Every refusal has a rule tag; no input may reach a panic.** Rewards come from untrusted generated programs: they run in a sandbox with a time and memory limit, and a crash of the program is a reward of zero, never a crash of the trainer.
* **No source file over 2,000 lines**; split by concern.
* **One GPU job at a time.** Check for other jobs (`pgrep`, `top`) before a run; stop a run that swaps.
* **Pin cancho-gpu by commit** (as cancho-gpu pins the compiler), and say in every result which commit of cancho-gpu produced it.
* **Implement in cancho where cancho can do it**, and use Python only where cancho-gpu's own examples do (driving sessions, plotting, comparing with torch). **[open]**: the split of the loop's code between the two is decided in R2 once the session driver's interface has been read.

## 11. R0 harness probe (2026-11-04): what cancho-code's eval offers as a reward

Read and run on cancho-code at `6fcac18`, compiler `target/debug/cancho` of this repository (a **debug** build; release timings are **[unknown]**). Nothing was changed in cancho-code.

* **[read]** The scoring entry point exists and is a file-to-score call: `CANCHO=<compiler> python3 eval/audit_<item>.py <project.cho>` prints per-function-group `passed/of` and `TOTAL n/N`. There are 14 audits (`basics`, `tokenbucket`, `roman`, `base64`, `duration`, `editdistance`, `sortedmap`, `jsonptr`, `expr`, `glob`, `semver`, `ini`, `csv`, `multi`); `tasks.json` lists 13 tasks. Oracle sizes run from 25 (`sortedmap`) to 873 (`multi`) cases. The audit wraps the candidate (strips `main`, makes functions `pub`, adds test helpers) and runs `cancho test`.
* **[measured]** `roman/reference.cho` scored 439/439 in three runs (0 disagreements; R0(a) wants 20, so this is 3 of 20). The empty program (`edition 7;` only) scored 0/439 with the compiler's error per group. Wall time per score was 7.4 to 10.4 s with 1.3 s user CPU, so most of it is waiting (compile or process startup), **[unknown]** which.
* **[read]** Safety: the only limit is `timeout=300` on one `cancho test` call (`audit_basics.py`; `audit_roman.py` has none). There is **no memory limit and no sandbox**. ## 12. R0 task set: small single-function tasks (decided 2026-11-04, before the code)

> **Corrected 2026-11-04 (section 14): the Python grader, generator and `prompt.json`/`cases.json` described here were replaced by cancho.** What still holds: the task shape, the independent oracle, the split idea (now FNV-1a, not SHA-256), the reward `passed/of` plus `solved`. What changed: `tasks/<id>/` holds `task.spec`, `oracle.cho` and `reference.cho`; the grader is `rl grade`.

The maintainer chose to write small tasks rather than relax R0(b) (section 11). The design:

* **A task** is one pure function over `int`/`bool` (effect row `[]`), the shape of cancho-code's `basics` item, so the existing way of testing (a generated `cancho test` file, one `test_cNNN` per case, grouped by function) carries over. It has: `prompt.json` (name, signature, description, a few visible examples), `cases.json` (hidden oracle cases, JSON lines of `{args, expect}`), `reference.cho`.
* **Oracle independence:** `cases.json` is computed by a Python function written separately from `reference.cho`, plus hand-computed anchors asserted in the generator (as `basics/oracle.py` does). The reference must score full on its own cases; a case set that its reference fails is a bug in one of the two.
* **Split:** a task is held out when `sha256(id)` mod 4 == 0 (a fixed rule, not a choice made after seeing results). Held-out `cases.json` is read only by `grade.py` when called with a held-out id and never copied into any prompt or training record.
* **Grader `grade.py <id> <candidate.cho>`:** builds the test file, runs `cancho test` in a child with a wall-time limit and `RLIMIT_CPU`; prints one JSON object `{id, passed, of, reward, status}` with `reward = passed/of` and `status` one of `ok`, `build_error`, `trap`, `timeout`. Any child failure is reward 0; the grader itself never raises on a candidate. **[unknown]** whether macOS enforces `RLIMIT_AS`/`RLIMIT_DATA` for the compiler's output; the memory limit is set and its effect is measured before it is claimed.
* **Count:** the target stays 200. The first commit builds the machinery and a first batch; the number reached is stated in the commit, not the target.
* **Sandbox note:** the candidate is a cancho program compiled by `cancho test` with no declared effects, so it cannot reach the filesystem or network by language rule **[read: cancho's effect rows, AGENTS.md]**; the limits cover only loops and memory.

## 14. The package is cancho; Python is a comparison helper (decided 2026-11-04, before the port)

The maintainer's rule: **cancho-rl is pure cancho; Python may only be a helper that compares with other frameworks, or not be used.** Sections 12 and 13 built the grader, generator and oracles in Python; that is **corrected here**: those files are a first version, to be replaced, not kept. The pattern is the sibling's: cancho-opt is cancho with `scripts/*.py` that only compare it with scipy.

* **In cancho (the package):** the task spec parser, the test-file composer, the grader (spawn `cancho test` under a deadline, parse its summary), the task oracles (`tasks/<id>/oracle.cho`, written in a different style from `reference.cho`: brute force where the reference is clever), the JSON answer, and later the rollout/advantage/loss code that is not a kernel. Binary `rl`, built with `cancho build --bin rl`.
* **Task format (no JSON in the data, so no Python to produce it):** `tasks/<id>/task.spec`, line oriented `key: value`: `name`, `ret` (int or bool), `desc`, `example` (a call and its value, hand-checked), `grid` (one line of ints per parameter; the cases are their product, every k-th taken above 250) and `case` (explicit tuples). `oracle.cho` defines `o_<name>`; the composed test file asserts `name(args) == o_name(args)` per case, so no expected values are stored.
* **Python's remaining role (`scripts/`):** `crosscheck.py` evaluates the same functions with Python's own `math`, on the cases `rl cases <task>` prints, and fails on a disagreement: an independent oracle in another framework, as `check_scipy.py` is for cancho-opt. It is not needed to build, grade or train.
* **Siblings to reuse, by commit pin (`cancho add`), not by copying and not by shelling out** **[read: alpibrusl/cancho-tools and cancho-stats, shallow clones, 2026-11-04]**: `cancho-tools` has a `contract` package (flag parsing with rule-tagged refusals, a JSON answer envelope, bounded `read_all`, atomic writes) and a `run` tool that starts a program with a deadline and an output cap, the shape this grader needs; `cancho-stats` has a percentile bootstrap (`lib/csvx/boot.cho`), which is the success rule's interval in section 5. Which of them cancho-rl takes as a dependency is decided when the code first needs it; this section does not claim they fit.
* **Split rule corrected:** the hash is FNV-1a over the task id, mod 4 == 0 held out (the SHA-256 of section 12 needed a library the first tool does not otherwise use). Nothing was trained on the old split.
* **Before the Python files are deleted** the cancho grader must reproduce the Python grader's results: all 34 references full, the probes of section 13 at the same scores. Until then they remain, marked as superseded.

## 28. R2, step 1: the weighted-loss contract, read (2026-11-05)

Read from `cancho-gpu/examples/qwen/ce_grad.chx` and `qwen_train.py` (commit `b5dd6a5`); nothing run.

* **[read] The kernel already takes a row weight.** `ce_grad` computes `dl[i, :] = (softmax(logits[i]) - onehot(target[i])) * wt[i]` as f16 for each row `i` (one row per token position of the batch), where `wt` is an `f32[r, 1]` input. In the training session `wt` is the resident file `wscale` that the session writer fills on the host: `wcount * loss_scale`, with `wcount` 1 for a position that has a next token and 0 for the last position of a sequence (`qwen_session.py`/`qwen_train.py`: `S.put(p("wscale"), wcount * loss_scale)`).
* **[derived] So the policy-gradient loss needs no kernel change.** Put `wt[i] = loss_scale * A_g * m_i` where `A_g` is the advantage of the completion the position belongs to and `m_i` is 1 on the completion's tokens and 0 on the prompt tokens: the row's gradient is then `-d/dlogits` of `A_g * log pi(token)` (the sign convention to be checked against torch, as R2's gate does). This is the same loss as `scripts/r1_grpo.py`'s token-mean loss, up to the normalisation: the optimiser divides by the number of *counted* positions (`qwen_train.py`: "the optimiser divides it and the number of counted positions out"), which must be the number of completion tokens used, not all positions. [derived, to be tested in R2]
* **[derived] Two things to watch.** (1) The gradient is stored as f16 with `loss_scale` 16 by default: advantages are of order 1 and signed, so a range check like the one in `range_check.py` is needed with the advantage folded in. (2) The kernel's weight is **per position, not per sequence**, which is what is wanted; sequences in a batch are `nb` rows of `t` = 512 positions each, and `t` must be a multiple of 64 (resident.md section 20), so a prompt of about 700 tokens plus a completion needs the longer `t`, which section 20 says was only run at 512. **[unknown]** whether `t` = 1024 fits and fits in time: this is the first thing to measure, because the primer prompt alone is longer than 512 tokens.
* **[read] The weight is not an input per request.** `wscale` and the batch (`x0h`, `tgt`) are tables indexed by step, written when the session file is written (`tab(..., nsteps)`); a request is a count of steps. A policy-gradient iteration needs a new batch and new weights each iteration, from a policy that has just changed. Two ways, both in cancho-gpu: (a) a session per iteration, started from the previous adapters and optimiser state (`state`, `first_step` and `save_state` exist for continuing a run, section 19 there), at the cost of loading the 1.5B weights again each time (**[unknown]**: seconds); (b) an `input` directive that carries a tensor (today `input` carries numbers), so one resident session takes a new batch per request. (b) is the right one and a change in cancho-gpu; (a) is what exists, and R2 can use it because R2 is one fixed batch.
* **[unknown] and next:** the cost of (a) per iteration; `t` = 1024; whether the session writer (Python today) can be replaced by cancho without changing a byte of the session file (the test is to write the same file from both and compare). The last is the first cancho code of R2.

## 31. R2, step 4: the advantage and the batch, in cancho (2026-11-06)

* **What it is.** `rl pack SAMPLES PREFIX NB T PAD` (`lib/rl/adv.cho`, `lib/rl/pack.cho`): samples in, one training batch out. The samples file is JSON lines, the samples of a prompt together: `{"group", "reward", "prompt": [ids], "completion": [ids]}`. Advantages are group-normalised over each maximal run of lines with the same `group` by `r1_grpo.py`'s rule: `(r - mean) / (std + 1e-4)`, `std` the unbiased (n - 1) one, and a group whose rewards are all equal, or that has one sample, gets 0. A sample whose advantage is 0 is dropped (R1 does the same). The kept samples are the rows of one `[NB, T]` batch (prompt, completion, then `PAD`); the rows after them are all `PAD` with weight 0. Outputs: `PREFIX.tokens.i32` (int32 little-endian) and `PREFIX.weights.f64` (binary64 little-endian), which are `qsw write --tokens` and `--weights`. Nothing is written when no sample is kept (the caller skips the update, as R1 does with `if seqs`).
* **The weight, and the normalisation (the part that is easy to get wrong).** The weight of the position `i` of a row, whose target is the token `i + 1`, is the sample's advantage when that token is a completion token, else 0, **times `NB (T - 1) / N`**, `N` the completion tokens kept. Reason **[read]**: cancho-gpu's optimiser divides the gradient by the constant `NB (T - 1) loss_scale` written into the session (cancho-gpu `docs/qsw.md` section 3), not by the number of weighted positions; scaling the weights by `NB (T - 1) / N` makes the update the mean over the `N` completion tokens, which is what `r1_grpo.py` minimises. (Section 30's check divided by `N` itself with `split_grads`; this is the same thing done on the weights, so a real update needs no host-side division.) Adam is nearly invariant to the scale, its epsilon is not, which is why the scale is explicit and not left to chance.
* **[measured] Checks** (`scripts/pack_check.py`, in the gate; numpy is the independent computation, a comparison helper): tokens equal byte for byte and weights to 1e-12 relative (measured 1.7e-16) on random samples in six groups (mixed rewards, an all-equal group, a group of one, a group split in two runs); the summary counts; **kept 0 writes nothing**; 480 samples of 11 tokens in 60 groups; 4 samples of 1,100 tokens at `T` = 1,152; eight refusals, each a rule (`rl.pack.input`, `.sample`, `.overflow`, `.long`, `.write`, `rl.usage`). **Four mutants, each killed** (epsilon 1e-3, the biased standard deviation, the mask shifted by one, the missing `NB (T - 1)` factor). On section 30's real batch (rewards 0, 1, 0, 0 on its four sequences) the tokens come back equal to the generated ones and the weights equal `A NB (T - 1) / N` with `N` = 528.
* **A trap found and fixed on the way.** The first version kept its working arrays in a `region`, which holds 64 KiB in all, and trapped on the first real batch (lines of 7 KB); they are `box_slice` on the heap now, and the long-line case above is the test. No input reaches a trap is the rule of this repository's tools.
* **What this does not do, said so it is not read as done.** (1) **One batch is one optimiser step.** `NB` rows at a time, and R1's iteration is 32 completions: 8 sessions of 4 would be 8 updates, not R1's one update over 32. The options are all in cancho-gpu: gradient accumulation across requests, or `NB` = 32 in one session (about 55 GB at `T` = 1,152, over Metal's limit without the lean step **[estimate, section 29]**), or a different iteration shape (4 sequences an update, a measured change from R1, to be compared in R4). `rl pack` refuses more kept samples than rows (`rl.pack.overflow`) instead of choosing. (2) **Run on the GPU, [measured] 2026-11-06:** `rl pack` on section 30's four sequences with rewards 0, 1, 0, 0 (advantages -0.4999, +1.4997, -0.4999, -0.4999), its two files given unchanged to `qsw write --no-train --grads --weights` and the Metal runner, with the session's own constant divisor `NB (T - 1) loss_scale` (no host-side division by `N`), against peft float32 minimising `sum A CE / N`: **whole-gradient cosine 0.999952, norm ratio 1.00026**, smallest per-matrix cosine 0.9961, largest relative error 8.8%, sign right (`scripts/r2_grad.py PREFIX --nb 4 --t 1152`). That is the normalisation claim above, tested: the scale in the weights is the right one. One batch, one adapter draw, as in section 30. (3) The sampler that produces the samples file (R3) does not exist; the file's format is fixed here so it can be written to it. (4) The objective is the plain policy gradient of R1 (one update a batch, no clipping, no KL); a ratio and a clip need the old log-probabilities in the samples file and are not here.

## 32. R2, step 5: one update from several micro-batches (2026-11-06)

The problem of section 31: R1 makes **one** AdamW update over the 32 completions of an iteration, a session holds `NB` rows (4 at `T` = 1,152 is 29 GB; 8 would not fit), and a session step is one update. The answer measured here needs no kernel and no new directive.

* **[read, then measured] Two things the session already has.** (1) `table P.PARAM FILE S`: a resident file of `S` blocks, repetition `j` reading block `j mod S` (cancho-gpu `docs/resident.md` section 17) is how the batch itself (`x0h`, `tgt`) varies by step; `wscale` can be one too. (2) `checkpoint` saves the gradient outputs of the last step on request. **[measured]** `scripts/r2_accum.py`: two steps of one Metal session, the second batch the first with its rows reversed (tokens and weights), `wscale` a table of two blocks (the session line `resident cg.wt` changed to `table cg.wt ... 2 f32`): the gradient read after step 2 equals step 1's, **cosine 1.000000, norm ratio 1.00000**; the control with the resident `wscale` gives **cosine -0.011, norm ratio 124**. So per-step weights work and the check can tell.
* **What was built.** `qsw write --weights` accepts one block for each batch of `--tokens` and writes the table (cancho-gpu#123: byte for byte the Python writer's but `wscale` and that one line, in the gate, with a killed mutant); `rl pack` splits the kept samples into K = ceil(kept / NB) batches of `NB` rows and takes **`N` over all of them**, so each batch's gradient, divided by the session's constant `NB (T - 1) loss_scale`, adds up to the mean over every completion token of the update (`scripts/pack_check.py`: tokens and weights against numpy, the padded last batch, N over all batches; two new mutants killed).
* **[measured] The update, end to end** (`scripts/r2_batch.py --samples`, `scripts/r2_update.py`): 8 real completions of the Instruct model for `lcm` (rewards 0 0 0 0 0 1 1 0; advantages -0.54 and +1.62), `rl pack` into 2 batches of 4 x 1,152 (1,064 completion tokens), `qsw` writing a session of 2 steps with the table, the Metal runner doing one request and one `checkpoint` per step, the two gradients summed on the host, against peft float32 minimising `sum A CE / N` over all 8 sequences (micro-batches accumulated, which is the same loss): **whole-gradient cosine 0.999984, norm ratio 0.99995**, smallest per-matrix cosine 0.9992, largest relative error 3.9%, sign right. Two steps with a checkpoint each took 7.5 s (4.3 with the compile, 3.1).
* **[estimate] Cost of an R1-sized update.** 32 completions are 8 steps: about 4 s + 7 x 3.1 s = **26 s** plus the weights' load at the session's start. The session must be started again for each update, because the host changes the adapters (below); the first request of a 1.5B session took 4 to 9 s in sections 29 and here. R1's whole iteration was about 200 s including generation, so training stays the minor part.
* **What is still not built (and is the rest of one update).** (1) **The host AdamW step**: sum of the K gradients (done here, in numpy), **global-norm clipping to 1 (R1 clips; the session's own optimiser has no clip, so the host path matches R1 better than the in-session one would)**, AdamW on the per-projection matrices, the new adapters written for `qsw --adapters` (per-projection binary64, which is what the writer takes). In cancho, in cancho-rl; not written. (2) The moments: they persist across updates, so they are a file of the loop (the writer's `state` continuation is not covered by `qsw` yet). (3) Adapters are rewritten and the session restarted every update: the restart cost, measured above, is the price of not adding an `input` for adapters to cancho-gpu. (4) One adapter draw, one group of samples, `T` = 1,152: as in sections 30 and 31.

## 33. R2, step 6: the optimiser step on the host (2026-11-06)

Section 32 left the rest of one update: sum the K micro-batch gradients, clip, apply AdamW, write the next adapters. Done in cancho, outside the session, because the session's own optimiser has no clipping (R1 clips the global norm to 1) and has to run once per step, not once per update.

* **The pieces.** `qsw split` (cancho-gpu#123) turns the fused f32 gradients of a step into per-projection **binary64** gradients in the order of `qsw write --adapters`: held to `qwen_train.split_grads` **byte for byte** on random gradients with zeros, a negative zero, subnormals and 3e38 in three shapes (two bugs the check found and I fixed: the sign of zero, and the exact value of an f32 subnormal). `rl adamw CONFIG PARAMS M V OUT GRAD...` (`lib/rl/adamw.cho`) sums the gradient files left to right, takes the global norm, multiplies by `min(1, clip / (norm + 1e-6))` and applies the AdamW update of `torch.optim.AdamW` (non-amsgrad), writing `OUT.params.f64`, `OUT.m.f64` and `OUT.v.f64`; `-` for M and V is the first update. Everything is a flat binary64 file, so it knows nothing of the model, and the moments are just two more files of the loop.
* **[measured] Against torch** (`scripts/adamw_check.py`, in the gate when torch is installed): `torch.optim.AdamW` after `clip_grad_norm_`, float64, six updates in a row on 5,000 values with the gradient of each the sum of three files: parameters and both moments agree to **1.9e-11, 1.4e-11 and 4.1e-11** (R1's settings, weight decay without clipping, and a clip that only the later gradients reach: clipped in 6, 0 and 3 of 6), the norm to 4e-15. The arithmetic is the same but not in the same order, so this is not bit equality. Six mutants (the first moment weight, the second bias correction without its root, no weight decay, the missing 1e-6, subtracted gradients, the clip factor's floor) each fail the check.
* **[measured] A real update, end to end** (`scripts/r2_update.py --step`; the same 8 completions as section 32; adapters with B ~ N(0, 0.02^2), one draw): 2 Metal steps, `qsw split` of each, `rl adamw` with R1's settings (lr 1e-4, no weight decay, clip 1) on **18,464,768 values in 0.9 s**. The gradient norm is **0.4907, torch's too** (so no clipping here, factor 1.0). The move of the adapters against torch's (peft gradient, `clip_grad_norm_`, `torch.optim.AdamW`): **cosine 0.99698, norm ratio 1.00000, 0.19% of the elements move in the opposite direction, the largest difference 2 lr**. That is the first AdamW step: it moves every element by about `lr` whatever its gradient, so an element whose gradient is within the noise of the f16 session flips between +lr and -lr; the 0.997 is that noise, not a systematic difference (the gradients themselves agree to cosine 0.99998, section 32). Later steps, with moments, move by averaged gradients and will be less sensitive; **that is [unknown] until R4 runs several updates**.
* **What is built now, from samples to adapters:** `rl pack` -> `qsw write` (K steps, per-step weights) -> Metal (a step and a `checkpoint` each) -> `qsw split` (each) -> `rl adamw` -> new adapters and moments. Every link is held to a reference on its own (numpy, the Python writer, `split_grads`, torch) and the chain to peft/torch on one real batch.
* **Still not built, said so it is not read as done.** (1) **The driver**: nothing yet runs this chain in a loop (start the session, K requests, the file shuffling, the restart each update); it is a cancho program of file moves and `exec`, and its cost per update is the session's start (4 to 9 s, section 29) plus the above. (2) **R3, the sampler**: the samples file has no producer in cancho; batched sampling speed on the 1.5B is still the largest unknown. (3) The evaluation of a policy (R1's held-out solve rate) in cancho needs the sampler too. (4) One adapter draw and one batch throughout; B = 0 at the true start, where only B's gradient is non-zero, is a different first update.

Until it exists, R4 could take its samples from torch (`scripts/`, a comparison helper), with every other step in cancho, to measure the training half of the loop first; that is not the goal as stated (training and sampling in cancho) and is offered only as a way to get an earlier R4 number, if the maintainer wants one.

## 36. R3, step 2: decode attention measured, and the rest of a decode step (2026-11-06)

* **[measured] Attention is at the bandwidth the products reach.** Two kernels in cancho-gpu ([cancho-gpu#129](https://github.com/alpibrusl/cancho-gpu/pull/129), `docs/kernels.md` section 8): `attention_scores_b` and `attention_pv_b`, the batched versions of the existing split decode attention, with a cache and a mask for every sequence (the sequence is a grid axis; offsets stay affine) and heads of 128 (the scale is a literal). Held to the interpreter, a float64 reference and a Metal GPU (worst relative difference 1.7e-6 at 4 sequences of 1,152 positions). `scripts/r3_attention.py` (28 layers on random f32 caches, the caches read in full every step whatever the lengths): **8 sequences of 1,152 positions 1.73 ms a step, 32 sequences 6.77 ms (312 GB/s of keys and values)**. f16 caches would halve it. No further attention work is indicated.
* **[estimate] So far a step is** products 14.8 ms (section 35) + attention 6.8 ms = 21.6 ms of the 32-row step; 400 steps are 8.6 s, against torch's roughly 60 s of generation. The rest of the step is not measured.
* **[derived] A constraint that shapes the design: the logits cannot go to the host.** A session answers numbers as text (about 11 numbers a microsecond: section 35's mismeasurement showed 32 x 152,064 numbers cost 55 ms). Sampling on the host would add that to every one of 400 steps. **So the sampling happens on the device, the answer of a step is the 32 token ids, and the token feeds the next step on the device** (`steps` and `carry`, cancho-gpu `docs/resident.md` section 12, already loop a session without the host).
* **[derived] What a decode step still needs, each checkable alone:**
  1. *Embedding of the sampled token on the device.* No data-dependent gather in the surface (offsets are affine), so a one-hot row times the embedding table, a product the size of the output product (0.47 GB read, about 3 ms [estimate]); `onehot_h.chx` exists from the training session.
  2. *Small kernels for rows with their own positions:* the rotary embedding with `cos` and `sin` rows as data per step (a `table` read a row per repetition, as the training session does for the sequence), `kv_write_b` (the existing `kv_write` has one `sel`/`keep` pair for all sequences; this one takes `[nb, tmax]`), the norms (`rms_h` takes any number of rows), SwiGLU, the residual adds, the q/k/v biases. Mostly existing kernels at `r` = 32.
  3. *Sampling on the device:* temperature 0.8, no top-p or top-k. The surface has no integer type or hash, so the random numbers are **data**: one uniform a sequence and step (400 x 32 floats a table, a `table` read a row per repetition). Inverse-CDF sampling then needs a prefix sum over 152,064 probabilities, which `matmul` with a lower-triangular matrix of ones does (two levels: chunk sums, then within the chosen chunk), and the first index whose cumulative probability reaches `u` is found with `step`/`relu` comparisons. Checked as a distribution against torch's `multinomial` on the same logits (a chi-squared on many draws), since the sequences differ draw for draw. **[unknown]**: whether the two-level scheme is fast enough (the triangular matrices are resident, about 5 M floats for the chunk level).
  4. *The loop:* a request of N steps runs the step N times; the sampled one-hot is carried to the embedding product; the 32 ids of every step are written where the host can read them at the end (a table cannot be written; `save` on `checkpoint` writes the last step's outputs only, so the ids need an accumulating buffer, a carried vector extended by one slot a step with the `sel` trick of `kv_write`). **[unknown]** and the first thing to build for it.
  5. *Prefill:* the 4 distinct prompts (623 to 725 tokens) through the training forward kernels at `nb` 4 x 1,152, with the keys and values written into the 32 caches (the 8 samples of a prompt share a prefill and copy it). **[unknown]**: the forward session saves no keys and values today.
  6. *Adapters:* merged into the f16 weights once an iteration (a host pass over 2.6 GB, cancho, seconds); the sampled policy then differs from the trainer's by the f16 rounding of `W + s B A`, which R4 must measure.
  7. *The whole against transformers:* greedy tokens and the five largest logits on the first steps, as `docs/inference.md` section 2 does for the 0.5B.
* **Order.** (a) the on-device sampler on its own (3), because it is the least known and nothing else depends on its form; (b) the accumulating token buffer and the carry loop on a toy step (4); (c) the step itself from existing kernels (1, 2) with its timing; (d) prefill (5); (e) 6 and 7. The first measurement that can still sink the plan is the sampler's time at 32 x 152,064.

## 37. R3, step 3: the sampler, on the device (2026-11-06)

* **Built and measured** ([cancho-gpu `docs/sampler.md`](https://github.com/alpibrusl/cancho-gpu/blob/main/docs/sampler.md) once merged; draft PR in cancho-gpu): seven kernels doing temperature sampling by inverse CDF over the padded vocabulary (152,064 = 2,376 chunks of 64), the uniform of each row and step supplied as data. The surface has no scan, so the cumulative distribution is two levels of prefix sums, each a product with a lower-triangular matrix of ones (over the chunks, then inside every chunk; only the chosen chunk's count is used, since offsets are affine and a data-dependent window cannot be read).
* **[measured] 32 rows x 152,064 columns: 0.99 ms a step on Metal.** Section 36 left this as the unknown that could sink the plan; it is a thirtieth of the 30 ms a step budget.
* **[measured] Held to numpy.** At the real size on Metal, **4,800 draws equal the float64 inverse CDF of the same logits** (none near a boundary differed), the same uniforms give the same tokens, **3,000 draws from a row against its softmax: chi-squared 79.2 on 64 bins (limit 114.9)**, no padding column ever drawn; the same on the CPU interpreter at a small size, seven kernels against the interpreter on the GPU (1.4e-7), six mutants killed (one, the padding mask in the maximum, survived a first test whose padding logits were only +8 and is caught with +100).
* **What the next steps inherit.** The sampler returns the 1-based token ids, the convention of `ce_stats` and `onehot_h`, so `onehot_h` followed by the embedding product is the next layer's input with no host trip. The random numbers are data: one uniform a row and step, a request line for a step or a `table` for a request of many; producing them (a seeded generator in cancho on the host) and the seed discipline for R4 are not done. **Not built:** the accumulating token buffer and the carry loop (design 36, item 4), which decide whether a request of N steps can run on the device without the host; that is next, on a toy step.

## 38. R3, step 4: the decode loop stays on the device (2026-11-06)

Section 36 listed the id-accumulating loop as the second thing that could sink the plan. Built on a toy step and measured ([cancho-gpu `docs/sampler.md`](https://github.com/alpibrusl/cancho-gpu/blob/sampler/docs/sampler.md) section 6, `tests/carry_dev.py`, draft PR cancho-gpu#131).

* **What it is.** A request of N steps in which every step turns the previous ids into a one-hot (`onehot_h`), multiplies it by a table (the toy "model" is a bigram table, so there is an exact numpy counterpart), samples (the seven kernels of section 37) and writes the ids into slot j of a carried buffer (`tok_acc`, the `sel`/`keep` trick of `kv_write`, both tables read a block a repetition). The ids feed the next step by `carry`; the uniforms are a `table` too. **The host sends "N" and reads the N ids of every row at the end.** Nothing new in the session: `steps`, `carry` and `table` (cancho-gpu `docs/resident.md` section 12) plus one small kernel.
* **[measured] Held to numpy.** 32 rows x 64 steps over a 1,536-column vocabulary with 100 padding columns at +100: **all 2,048 ids equal the float64 inverse CDF run step by step with the same uniforms**, from two requests (48 steps, then 16: a second request continues the tables and the carried state), on the CPU interpreter and on Metal; no padding column drawn; a fresh session gives the same ids; the ids not carried and the slot selector shifted by one are each caught (mutants). The smallest relative distance of a uniform to a boundary in the run was 5.9e-7, so a boundary flip is not excluded in general (about 1e-7 a draw), only absent here.
* **[measured] 0.17 ms a step** for this toy step's 14 programs (about 12 microseconds a program): the launch overhead a full step of about 450 programs will pay is **about 5 ms [estimate]**.
* **[estimate] So a whole step is now** products 14.8 + attention 6.8 + sampler 1.0 + embedding product about 3 + launch overhead about 5 + the small kernels' own work = **about 30 ms**, and 400 steps of 32 samples about **12 s**, against torch's 60 s of generation. The estimate is the sum of measured parts; the assembled step is not built.
* **A bug found, filed here not fixed:** a session whose `program` line names a kernel file by a path containing `..` makes `cancho-gpu-session` die with SIGILL and no message (a normalised path runs): against the repository's rule that no input reaches a panic.
* **Left for R3:** (c) the step itself from existing kernels (rms/rotary/biases/SwiGLU/residuals at 32 rows with per-row positions, `kv_write_b`), with its timing; (d) prefill, which writes keys and values the forward session does not save today; (e) the adapters merged into the f16 weights once an iteration, and the comparison of greedy tokens and top-5 logits with transformers. The step (c) and the prefill (d) are independent and the first is the larger.

## 39. R3, step 5: the real decode step, held to transformers (2026-11-06)

* **Built and measured** ([cancho-gpu `docs/decode.md`](https://github.com/alpibrusl/cancho-gpu/blob/decode-step/docs/decode.md), draft PR cancho-gpu#132 which includes #129 and #131): `qsw decode` writes a session of the whole decode step of Qwen2.5-1.5B for up to 32 sequences: the ids as a one-hot times the transposed embedding, 28 layers (the new `dec_post` for the biases and the rotary embedding at each sequence's own position, `kv_write_b` for the caches, section 36's attention, the products of section 35), the output product, the sampler of section 37, the ids collected and carried (section 38). A request of N steps returns the N ids of every sequence; the host sends N. Prompts are fed one token a step.
* **[measured] Held to the float64 forward** (a random 2-layer model of the real layer shapes, 12 steps teacher-forced): the largest difference 1.7e-4 of the largest logit, cosine 1.000000, arg max agreeing at all 24 clear-cut positions.
* **[measured] Held to transformers on the real Qwen2.5-1.5B-Instruct** (two chat prompts of 42 and 48 tokens, float32 on the CPU): free-running, **all 24 generated tokens agree with `generate(do_sample=False)` for each prompt**; teacher-forced on those sequences, the arg max agrees at **all 138 positions, the smallest cosine of the logits is 0.999998**, and the sampler drew the arg max of its own logits at all 138. Four mutants of the decode test (the rotary sign, the cache `keep` read as `sel`, the attention mask subtracted, the prompt flag ignored) each fail it.
* **[measured] Cost.** **35.6 ms a step at 32 sequences with 1,152-position f32 caches** (7.7 GB peak), 11.2 ms at 8 sequences with 256-position caches. **400 steps for 32 samples take about 14 s, against torch's 60 to 66 s of generation in R1 (section 27): about 4.3 times faster**, before prefill. Section 36's estimate of about 30 ms was close; the costs are not broken down (products 14.8 ms and attention 6.8 ms measured alone, the rest is the cache rewrite of `kv_write_b`, the small kernels and about 450 launches).
* **Two traps worth keeping.** (1) Qwen's `generation_config.json` has `repetition_penalty` 1.05, which transformers applies in greedy generation: with it the decode diverged at the first repeated word while the logits agreed; the comparison must pass `repetition_penalty=1.0`. (2) The diagnosis took a teacher-forced comparison of the logits, which separates "the logits differ" from "the choice differs": the first guess (the sampler's near-ties) was wrong and cost two runs.
* **What R3 still lacks.** (a) **Prefill**: a 700-token prompt costs 700 decode steps (about 25 s) as it stands, against a prefill of the 4 distinct prompts through the forward kernels of a second or so [estimate]: it writes keys and values the forward session does not save, and `qsw decode --pos0` is there for the sequences that start after it. (b) The adapters merged into the f16 weights once an iteration, and the measurement of the policy mismatch that causes. (c) **The sampler as R4's rollout**: tasks, the chat template and `rl prompt` to tokens (a tokenizer in cancho: cancho-gpu has one), the stop at the end-of-turn token, the extraction and grading, and the group of 8 samples per prompt. (d) f16 caches (about half the attention and rewrite), only if the step proves the bottleneck of an iteration.

## 40. R3, step 6: prefill (2026-11-06)

* **Built and measured** ([cancho-gpu `docs/decode.md`](https://github.com/alpibrusl/cancho-gpu/blob/prefill/docs/decode.md), draft PR cancho-gpu#133, stacked on #132): `qsw write --no-train --kv-export DIR` writes the **training forward pass** as a forward-only session (no head, loss, backward pass or optimiser; with the adapters if the adapters file has any) over the distinct prompts, and instead saves each layer's keys and values, turned by a new kernel `kv_import` into the layout of the decode caches with **eight copies of each prompt's** (R1's group of 8 samples). `qsw decode --kv-dir DIR --pos0` then starts each sequence at the last token of its prompt.
* **[measured] Held to transformers on the real Qwen2.5-1.5B-Instruct:** two prompts (42 and 48 tokens) prefilled, then 16 sequences decoded from those caches: **every one of the 16 generates the 24 greedy tokens of `generate(do_sample=False)`**. The training sessions are untouched (byte for byte the Python writer's in the gate), `kv_import` is exact on Metal.
* **[measured] Cost** (4 prompts of 1,152 positions, the real 28 layers): **1.18 s** a prefill request, 1.4 s to write the 56 cache files (2.1 GB) on the `checkpoint`, 24.8 GB peak (so it runs before the decode session, not beside it). About 4 s of prefill for an iteration, against about 25 s for the same prompts through decode steps: with section 39's 14 s of decode for 400 steps, **a rollout of 32 samples is about 18 s + the session starts, against R1's 60 to 66 s**.
* **What R3 still lacks.** (a) **LoRA in the decode step**: the prefill applies the adapters (it is the training forward), the decode step does not, so a rollout of an adapted policy needs the low-rank products in each layer (about 4 small programs a layer: `x A^T` then `(.) B^T` added to the base product, reading the `Ah`/`Bh` files `qsw write` already writes) or the adapters merged into the f16 weights; the first is cheaper to run per iteration. (b) The **rollout glue**: chat template and `rl prompt` to token ids (a cancho tokenizer exists in cancho-gpu), the stop at the end-of-turn token (the host truncates), `rl grade` of each sample, advantages by `rl pack`. (c) The **driver**: prefill session, caches to the decode session, decode, grade, pack, `qsw` training session, `qsw split`, `rl adamw`, restart with the new adapters: a cancho program of file moves and `exec`. (d) The comparison of the policy sampled (f16 caches, f32 elsewhere) with the trainer's, as an importance ratio, only if R4 shows it matters.

## 41. R3, step 7: LoRA in the decode step (2026-11-06)

* **Built and measured** ([cancho-gpu `docs/decode.md`](https://github.com/alpibrusl/cancho-gpu/blob/decode-lora/docs/decode.md), section "LoRA"): `qsw decode --adapters DIR` replaces each of a layer's four projections by the base product, the adapter's two small products (`x Ah^T`, cast to f16, then `. Bh^T`) and an f32 add, reading the `Ah`/`Bh` files `qsw write` writes for the training session. A decode therefore samples from exactly the adapters the prefill and the training forward read, and nothing is merged into the 3 GB of weights.
* **[measured] Held to the float64 forward pass with adapters** (a random 2-layer model of the real layer shapes, a B of standard deviation 0.05, 12 steps teacher-forced): largest difference **1.8e-4 of the largest logit**, cosine 1.000000, arg max agreeing at 24 of 24 positions. The same logits without adapters are 0.145 of the largest logit away, so the test cannot pass with the adapters left out; a mutant that leaves them off the down projection only fails it (6.3e-2).
* **[measured] Cost** (the real 28 layers, 32 sequences, 1,152 positions): **43.0 ms a step against 35.8 ms without adapters** (+20%); 400 steps take about 17 s instead of 14 s. The 16 extra programs a layer are launches of small products; fusing them into the base products would recover part of it (not done). With the prefill of section 40 a rollout of 32 samples is about 21 s + the session starts [estimate: sum of the measured parts], against R1's 60 to 66 s.
* **[not verified]** The adapted decode against transformers with peft on the real model: the oracle is the float64 forward pass, and the prefill that applies the same adapters is held to transformers without them.
* **What R3 still lacks.** The rollout glue (chat template and tokenising, the stop at the end-of-turn token, grading, groups of 8), the driver, and the policy-mismatch check of section 40(d) if R4 shows it matters. The PR chain is long (cancho-gpu #132, #133 and this step on top; cancho-rl #24): merging it is the next housekeeping step.

## 42. R3, step 8: the rollout glue (2026-11-06)

Between the prompts of a task set and the samples file `rl pack` reads there was no producer in cancho. It is now a chain of small commands, each a cancho program, none needing the GPU, so each is held to its Python or transformers counterpart in the gate (the driver that runs the chain and the two GPU sessions is the next step):

1. `rl chat PRIMER TASKDIR` — `rl prompt` wrapped in Qwen2.5's chat template (the default system message, the user turn, the generation prompt). **[measured]** `scripts/chat_check.py`: for all **104 tasks** the text equals `apply_chat_template(..., add_generation_prompt=True)` of transformers as `r1_grpo.py` builds it, and the ids that `cancho-gpu tokenize` gives for it equal `tok(text)`: 0 of 104 differ; prompts are **623 to 725 tokens**.
2. `rl rollin PROMPTS GROUP T STEPS PAD SEED PREFIX` — from the `cancho-gpu tokenize` output of the prompts, the files of the prefill (`prefill.i32`, the prompts padded to T) and of the decode (`tokens.i32` the last prompt token of each of the prompts x GROUP rows, `lens.i32` all 1, `pos0.i32` length - 1, `uniforms.f64` from a seeded 31-bit Lehmer generator, `plens.txt`). **[measured]** `scripts/rollin_check.py` (4 prompts x 8): the layouts against numpy, 12,800 uniforms in [0, 1) with mean 0.504, std 0.2890 (0.2887 expected), chi-square 9.5 over 20 bins, no serial correlation, same seed same file, and four refusals by rule. The generator is 31 bits and a draw is capped below 1 - 2^-24 so that f32 never rounds it to 1.0; it is enough for sampling tokens, not for anything that needs more.
3. `cancho-gpu detokenize TOKENIZER IDS` (cancho-gpu `detokenize` branch) — the decode of ids to text that was missing. **[measured]** 0 of 461 records differ from `Tokenizer.decode`, over random ids (tokens ending inside a character, added tokens, bytes under 32), real text and the empty record.
4. `rl complete IDS GROUP STEPS PREFIX` — the decode's draws `[nb, steps]` (1-based) become, per sequence, the completion up to and **including** its first `<|im_end|>` (151645) or `<|endoftext|>` (151643), or all STEPS when there is none (cut off); `PREFIX.ids` is the same without the stop token (what the decode of `r1_grpo.py` returns with `skip_special_tokens`) and `PREFIX.meta` keeps the stop.
5. `rl extract DEC PREFIX` — the fenced ```cancho block of each decoded reply into `PREFIX.k.cho`, `r1_grpo.py`'s `extract` (nothing but a newline when there is no block, so the program does not build and scores 0).
6. `rl grade` as before, one process per sample (R1 ran six at a time).
7. `rl samples META PROMPTS TASKS RESULTS OUT` — the samples file: group = task name, the reward copied from the grade result (0 when the result is missing: a crash of the grader's child is no reason to crash the trainer), the prompt ids and the completion ids. `rl pack` reads it.

* **[measured] The chain held with no GPU** (`scripts/rollout_check.py`): eight replies written by hand (a reference solution, a wrong one with partial credit 0.538, prose, one cut off at the step limit, one followed by 100 more draws after its stop token, non-ASCII and quoting) encoded by transformers, laid out as a decode answer, sent through steps 4 to 7, and `rl pack` accepts the result: the completions equal the encoded ids up to the stop, the programs equal `r1_grpo.py`'s `extract` of transformers' decode (8 of 8), the rewards are the expected ones and the prompts are the `tokenize` ids. Two mutants (the end-of-text token not a stop, the position off by one) each fail their check.
* **Not measured (corrected 2026-11-06, section 43).** This section's check wrote the draws as plain integers; the real session prints them as shortest floats (`7.3595e4` for 73595), which `rl complete` read as 7 (it dropped the exponent): the first real run found it, `num_at` now applies the exponent and `rollout_check.py` writes the session's own format. The cost of the chain is in section 43.
* **What R3 still lacks.** The driver: prefill session, decode session, then this chain, the training session, `qsw split`, `rl adamw`, the restart with the new adapters. It is a cancho program of file moves and `exec`; a shell script first is the cheaper way to find out what the order and the restarts cost.

## 43. The driver, as a shell script: one whole iteration, measured (2026-11-06)

* **What it is.** `scripts/iterate.sh OUT ADAPTERS.f64` runs one GRPO iteration through the programs of sections 34 to 42, each a separate process, each timed: `rl chat` and `cancho-gpu tokenize`, `rl rollin`, the prefill session (`qsw write --no-train --kv-export`, adapters applied), `qsw decode --kv-dir --pos0 --adapters` and its session, `rl complete`, `cancho-gpu detokenize`, `rl extract`, `rl grade` (6 at a time, as R1), `rl samples`, `rl pack`, the training session (K steps, a `checkpoint` and a `qsw split` each), `rl adamw`. It is a script first on purpose: to find what the order and the restarts cost before writing the driver in cancho.
* **[measured] One iteration on the real model** (cancho-gpu `dcc7a59`, Apple M4 Max; 4 tasks `abs_val clamp gcd max4` x 8 samples = 32 sequences, 400 steps, temperature 0.8, the starting adapters r = 16 with B = 0, lr 1e-4): **about 63 s of wall clock from the first file to the new adapters** (20:09:03 to 20:10:06). By stage: prefill of the 4 prompts 2.8 s (a fresh session, compile included), decode 19.7 s, grading 32 programs 5.8 s, everything else in the chain under 0.1 s, the update (8 micro-batches of 4: 8 steps with a checkpoint and a `qsw split` each, one compile) about 28 s, `rl adamw` over 18.46 M values 1.8 s. All 32 completions ended on a stop token (none cut at 400 steps; 2,784 completion tokens, 87 on average); rewards: abs_val 6 of 8 solved, clamp 7, gcd 5, max4 5 solved and two partial (0.8, 0.83). All 32 samples kept (no group had equal rewards). The gradient norm was 0.197 (no clipping), the largest move of any element is lr (the first AdamW step), no NaN.
* **Against R1's torch loop** (sections 30 and 39: 198 to 240 s an iteration, generation 59 to 66 s, update 133 to 180 s): **about 3.3 to 3.8 times faster in total**, measured on one iteration of ours (not the same tasks or seeds as R1's logs: a comparison of a timing, not of learning). Generation here is 28 s (decode + prefill + grading) against 59 to 66; the update 28 s against 133 to 180. The estimate of section 39 (45 to 55 s) was low by about 10 s: the grading and the sessions' start-up.
* **What the first run found** (the reason to run it): (1) the answer-format bug above; (2) the script's own bugs (a padded `wc` count in a config, timing lines sent into the data files, a coprocess whose stdin was not closed so the script waited for the session until I killed it: the 603 s the script printed for the update is that wait, the step timestamps give 28 s).
* **Not measured.** Learning: this is one iteration, not R4. The policy mismatch between the f16-cache decode and the trainer (the sampled tokens' log-probabilities are not compared). A second iteration from `new.params.f64` with the moments (`M`, `V`, `STEP`): the script supports it, it has not been run. Peak memory of the two sessions in turn (one GPU job at a time; they run one after the other). The adapters of the starting point were written with the Python initialiser once (`qwen_ref.init_lora`, B = 0): the cancho side has no initialiser yet.
